◆设计 · 方法论底座（F1–F8）

architecture-design skill 的八条框架原则，是全部增量设计与复利回写的纪律基础。

F14A 分叉依赖

BA→(IA∥AA)→TA：BA 先行，IA/AA 并行双向对齐，TA 最后。

F2跨域一致性

AA 功能≥1 IA 实体支撑，IA 实体≥1 AA 功能消费；结构+语义双对齐（发布门禁）。

F3变更分叉级联

直接 / 间接 / 隐式三层次必覆盖。

F4DDD 聚合四要素

实体 + 值对象 + 聚合根 + 事务边界；仅业务服务有聚合。

F5限界上下文 / Context Map

语义边界 = L3 应用服务；映射 Shared Kernel / ACL / OHS。

F6CQRS 写读模型

事务型→写模型，分析型→读模型；Command/Read→写模型，Query 经阻断测试分流。

F7三维判定

失忆(归属) + 阻断(类型) + 孤岛(层级)。

F8增量 + 复利回写闭环

As-Is 冻结 + 版本锚点 → To-Be → 全局锚点复利。

4 · 关键脚本（零 / 低 LLM，4+1 个）

validate-frontmatter

校验三份增量 frontmatter 字段完整性（advisory，不引第三方 YAML 依赖）。

arch-merge

delta 以 append + 版本锚点合入全局，one change per run。

discovery-check

扫描重复/冲突 BC/聚合（机械查重；语义冲突归 LLM）。

api-index-gen

扫描所有 specs/*/api.md 生成 API-INDEX.md。

asis-extract

按版本锚点从全局抽取相关章节填入增量 As-Is（防漂移）。

prototype-sync

change 完成 → UX 增量 + design-system 迭代回写全局 prototype/ 与 design-system.md。

回写顺序（closing 期）：arch-merge → prototype-sync 顺序提交（同一 change closing 内），避免全局 docs/architecture/ 与 prototype/ 半更新态被下一 change grounding。

◎场景 · 适用与不适用

本方案回答"何时做架构/DB/API 增量设计与原型"，以及哪些项目最适合采用。

✅ 推荐采用

  • 架构设计：每需求做"增强"——对当前现状 + 需求对应架构变更做设计，并复利回写全局。
  • DB 设计：与架构同模式（每变更增量 + 复利回写全局）。
  • API 设计：主要在每变更需求内设计（不进全局层），经 execution-contract.md 被 build-executor 硬消费。
  • 原型设计：无应用、纯 CLI 插件，需零依赖、可离线的本地 HTML 原型。
  • 项目类型：大型功能开发、多人协作、长期维护、需 TDD + Review Gate 的棕地项目。

⛔ 不推荐 / 不适用

  • 一次性脚本 / 工具（无持续架构演进价值）。
  • 纯咨询 / 问答类任务（无实现闭环）。
  • 强依赖 GUI 设计软件的原型（Claude Design / Trae / Open Design 均不安装）。
  • 原型不放入 per-change overlay，错误归属会破坏两层产物层级模型。
  • 不要在未暴露 docs/architecture/ 与 prototype/ 的项目里直接套用（先补 Discoverability）。
核心准则：原型是全局一份、与 PRD 同级；版本演进靠 git 分支，不靠 change 内 v1/v2 目录。change 是实施工作单位，不是产品基线。

一设计目标（用户原话落地）

① 架构设计

每需求做"增强"——对当前现状 + 需求对应架构变更做设计；复利环节回写全局架构设计。

② DB 设计

与架构同样模式（每变更增量 + 复利回写全局）。

③ API 设计

主要在每变更需求内设计（不进全局层）。

④ 架构方法

DDD（领域驱动设计）。

⑤ 借鉴经验

借鉴 compound-engineering（复利工程）可补充本块的好经验。

⑥ 原型设计 v0.3 新增

全局一份、与 PRD 同级、随 PRD 版本 git 分支演进；change 引用全局原型作 UI 契约；设计系统由项目 config 注入、复利回写。

五每变更增量模板

5.1 architecture.md

---
cap_id: <cap>
date: YYYY-MM-DD
change_type: new | modify
bounded_contexts: [<上下文>]
aggregates_affected: [<聚合>]
cqrs: [write:<x>, read_model:<y>]   # read_model 承载 Read 指令与 Query
tags: [ddd, <领域>]
---
  • ## 现状快照(As-Is，冻结基线)：复制 docs/architecture/ARCHITECTURE.md 相关章节当前原文，记录来源锚点 ARCHITECTURE.md@<change_id>#<章节>。本变更内不可变，不得用"见全局第 X 节"活引用。
  • ## 本次架构变更(To-Be)：新增/调整限界上下文与 Context Map；聚合(实体+值对象+聚合根+事务边界)；CQRS 写读模型；4A 跨域对齐。
  • ## 架构决策(ADR)：决策与理由。
  • 硬规则：聚合仅存业务服务（数据/技术服务无聚合）；Query 经阻断测试分流。

5.2 database.md

---
cap_id: <cap>
date: YYYY-MM-DD
change_type: new | modify
entities_affected: [<实体>]
cqrs: [write:<x>, read_model:<y>]
oltp_olap: [oltp:<t>, olap:<a>]
tags: [db, <领域>]
---
  • 现状快照(As-Is，冻结)：同上机制。
  • 本次 DB 变更(To-Be)：实体+生命周期；聚合对应表/事务边界；写模型(OLTP) vs 读模型(OLAP，派生自写模型)。
  • 迁移策略：前向兼容 / 双写 / 回填。

5.3 api.md（仅每变更）

  • API 清单：端点/方法/职责。
  • 指令映射(L6)：每端点标 Command/Read/Query；Query 标阻断测试归属(业务/数据服务)。
  • 契约：请求/响应 schema、错误码、幂等。
  • 硬消费钉死（v0.3）：api.md 经 execution-contract.md 被 build-executor 硬消费（TDD 实现），不得仅作参考；跨 change 一致性由 API-INDEX.md 脚本兜底。

六全局架构 / DB 文档（分目录 + 瘦锚点 + 双视图）

  • 总览层（覆盖式当前态）：ARCHITECTURE.md 瘦锚点总览 = Context Map + 各 bc 链接 + 关键决策；DATABASE.md = 全局 DB 总览（实体+读写模型+OLTP/OLAP）。
  • 每上下文层（分目录，起步即建）：<bc>/context.md 承载聚合/实体/服务/读写模型/事务边界；<bc>/evolution.md 承载演进日志（append-only，含 change_id+来源）。
  • 三层内容（F 产出三层）：元素层（BA/IA/AA/TA 四域一等元素）→ 制品层（Context Map、业务流程图、CQRS 读写模型）→ 交付件层（架构评审文档，生成视图非手写巨著）。
  • 双视图：总览覆盖式当前态 + 各 bc 演进日志 append-only，防多版本矛盾。

6.1 技术锚点定性的设计影响与高质量可拓展保障 决策 3

两份独立文档

STRATEGY.md 答"做什么/为什么"(BA)，ARCHITECTURE.md 答"怎么建"(IA/AA/TA)；改业务不重写技术，改技术不污染策略（compound "Anchor not plan" 延伸到技术域）。

分目录 = 天然扩展点

每新增限界上下文 = 新增 docs/architecture/<bc>/ 目录，不膨胀单文件，检索粒度随规模线性可控。

命名注册表防语义漂移

元素层标准化命名（用户/客户/consumer 不并存），是跨上下文可拓展的术语基础。

双视图保证当前真相清晰

总览覆盖式当前态 + 各 bc 演进日志 append-only，扩展时不丢失历史。

跨域一致性门禁

每次回写跑 AA≥1 IA 实体（结构+语义双对齐），新 bc 接入不破坏既有对齐。

瘦锚点保障可持续

避免评审交付巨著，单人也能维护，架构资产随项目长期复利而非一次性文档。

七复利回写机制（借 ce-compound，已正名）

  1. 结构化 frontmatter：架构专用 schema（cap_id/date/change_type/bounded_contexts/aggregates/cqrs），非直接复用 schema.yaml。
  2. one change per run：一次回写一个变更 delta（变更可追溯、不混杂多变更）。
  3. 双视图回写：当前态覆盖 + 演进日志追加。
  4. 架构一致性/漂移检查（独立机制）：①结构冲突（重复 BC/聚合 key）②语义冲突（同义异名，按命名注册表）③跨域一致性门禁（AA≥1 IA 实体，反之亦然）。
  5. Discoverability 正名：在 AGENTS.md/CLAUDE.md 暴露 docs/architecture/ 与 prototype/（存在/结构/何时检索），使代理设计前"发现并查阅"。
  6. 下游检索复用：下一 change 设计前从 docs/architecture/ 检索相关上下文/聚合，grounding 用 CONCEPTS.md。
  7. 设计系统复利（v0.3 新增）：UX 增量若涉及设计系统迭代（新组件/新 token/新 anti-pattern），合并进全局 prototype/design-system.md，作项目级风格唯一真相源复利累积。

八全局文档组织（已定：起步即分目录）

用户决策：起步即按 bounded context 分目录 docs/architecture/<bc>/（非单文件分节）。这是 compound problem_type→directory 的真类比，也是高质量可拓展基础——每新增限界上下文 = 新增目录，不膨胀单文件，检索粒度与一致性检查随规模线性可控。

十五原型设计能力（新增，第 13–16 轮调研）

15.0 五方案对比结论

方案形态对"纯 CLI 插件"可用性结论
Claude Design对话生成设计/交互原型/幻灯片强依赖 web/desktop 画布，无纯 CLI不适合内嵌
Open Design本地优先开源替代；DESIGN.md + 调色板需本地 daemon + Vite React，非纯 CLI不内嵌；DESIGN.md 概念值得借鉴
Trae Work Design生成/迭代界面设计，导出 HTML/ZIP强依赖 GUI 画布不适合内嵌
spec-superflow handoff --type prototype验证变更设计可行性的 overlay纯 CLI 但仅草图，无设计系统、无闭环仅作可选草图旁路
本地 HTML 原型 skill（本方案）自包含 HTML 原型 + 内嵌 Tweaks + 设计系统板纯 CLI 产出、零外部依赖、可离线最优
硬约束：不安装/不调用任何 GUI 设计软件（Claude Design / Open Design / Trae 均不安装）。spec-superflow 的 handoff --type prototype 仅作可选可行性草图旁路，不复用其 per-change overlay 作为主机制。

15.1 两层产物层级模型（全局层 vs 变更层）

全局层 · 产品级

与 PRD 同级

  • prd/：PRD，有版本 v1→v2→v3
  • prototype/：原型，全局一份
  • design-system.md：全局一份，config 注入
  • architecture.md（docs/architecture/）：全局架构
  • api.md（API-INDEX.md 聚合）：全局 API 索引
  • src/：代码，全局一份
变更层 · spec-superflow change

从 PRD 拆解

  • specs/<cap>/：spec/design/tasks/execution-contract/architecture/database/api
  • 每个 change 走 8 状态机
  • 一份 PRD（某版本）可拆多个 change
  • change 是实施工作单位，非产品基线
PRD(vN) ──拆解──┬─▶ change-1 ─▶ spec-superflow（exploring→…→closing）
├─▶ change-2 ─▶ spec-superflow　　└─▶ change-3 ─▶ spec-superflow
全局 prototype/ ──（UI 契约参考）──▶ 各 change 的 build-executor
各 change 完成 ──（增量合并）──▶ 全局 architecture.md / api.md / prototype / src

15.2 原型迭代模型（全局一份，随 PRD 版本 git 分支演进）

  • 原型是全局产物（与 PRD 同级），物理一份，不是某个 change 的子目录。
  • 版本演进靠 git 分支：PRD 升版（v1→v2）时，原型在对应分支上演进（如 prd-v2 分支上的 prototype/ = v2 产品原型）。
  • PRD 有版本，原型/代码无多份；历史版本由 git 分支/标签保留。
  • change 引用全局原型（进 execution-contract.md）；change 不直接拥有原型文件。

15.3 产物维护（完整原型系统，全局一份）

prototype/ # 全局，一份，git 分支隔离版本
index.html # 入口 / 全局导航
pages/ # 多页面（首页/列表/详情/设置…）
components/ # 可复用组件，统一设计系统
assets/ # style.js / design-tokens.css
design-system.md # 本项目设计系统（config 注入，9 段 schema）
flow.md # 页面跳转 / 用户流
原型膨胀防控 / 分支约定（评审修正 C）：components/ 必须复用 design-system.md 定义的组件，禁止页面内联样式漂移；原型随 PRD 当前版本分支维护，change 引用其所在 PRD 版本分支的 prototype/，避免原型领先/落后于未合并代码分支。

15.4 配置驱动（插件通用 + 项目注入）

  • 插件通用：原型 skill 不固化任何公司/产品风格；PRD 模板与设计系统由项目级配置注入。
  • 项目注入点：prd.template / prototype.designSystem（9 段 schema：color/typography/spacing/layout/components/motion/voice/brand/anti-patterns + 5 方向确定性调色板）/ prototype.entry。
  • ⚠ 配置字段边界（评审修正 A）：三者为插件层扩展字段，非 spec-superflow 原生 schema；建插件时需实测 ssf runtime config --get prototype.designSystem 验证读取路径可用。

15.5 本地 HTML 原型 skill（零外部依赖内核）

  • 内核形态：自包含 HTML（CSS 进 <style>、JS 进 <script>，页面内 <div> Tweaks 控件替代云端工具栏），avoid remote dependencies，可完全离线。
  • 设计系统渲染：读取项目 design-system.md 渲染 token，保证风格与品牌一致。
  • 产出：prototype/ 完整系统，纯 CLI 产出，不依赖任何 GUI 设计产品。

15.6 与实施阶段衔接（闭环，两层）

PRD(vN) ──拆解──┬─▶ change-1 ─┐
                ├─▶ change-2 ─┼─▶ spec-superflow: spec-writer → contract-builder → build-executor
                └─▶ change-3 ─┘         （各 change 引用全局 prototype/ 作 UI 契约）
                                              │
        全局 prototype/ ◀── 增量合并 ────────┘（change 完成回写 UX / 架构 / API）
        compound 复利回写: design-system.md / architecture.md / api.md
  • 原型（全局）→ 架构：原型确认的 UX 流向全局 ARCHITECTURE.md 限界上下文映射（DDD）。
  • 原型 → API：原型交互 → 端点设计 → 流入 execution-contract.md + build-executor。
  • 原型 → 开发：全局原型作 UI 契约参考进 execution-contract.md，build-executor 按契约 + TDD 实现。

15.7 I/O 钉死（补全前 12 轮三处未定义）

  • I/O-1：design.md ↔ architecture.md 关系：design.md 是每变更架构一等公民（随 change 状态机走，不可变）；全局 ARCHITECTURE.md 是跨 change 技术锚点（复利回写目标）。change 完成 → 其 design.md/增量 architecture.md 的 delta 增量回写全局，design.md 本身保持不可变。
  • I/O-2：api.md 硬消费：每变更 api.md 经 execution-contract.md 被 build-executor 硬消费（TDD 实现），不得仅作参考；跨 change 一致性由 api-index-gen 脚本兜底。
  • I/O-3：tasks.md 引用架构/API：tasks.md 显式引用本 change 的 architecture.md/api.md 章节锚点，不得活引用全局；build-executor 按 tasks + execution-contract + 全局 prototype/ 实现。

15.8 复利回写设计系统

  • 设计系统由项目 config 注入的 design-system.md（9 段 schema + 5 方向调色板，项目资产）。
  • change 完成 → UX 增量若涉及设计系统迭代 → 经 prototype-sync 合并回全局 prototype/design-system.md，作项目级风格唯一真相源复利累积。
  • design-system.md 回写发生在项目内，插件保持通用、不固化任何风格。

16.3 核心约束

  • 零依赖/可离线：data-testid 为纯 HTML 属性，不引入 JS/CSS/构建/Playwright；Playwright 仅进用户项目，不进插件。

16.4 data-testid 契约

  • 命名层级：场景级 S-{nn}-{slug}、页面级 P-{xx}-{slug}、元素级 {语义名}（如 create-btn）。
  • 选择器优先级：getByRole > data-testid > id > getByLabel > CSS/XPath（禁用于新测试）；禁止 waitForTimeout。
  • 打标纪律：场景/页面级必带；元素级仅关键交互锚点带，内部优先 getByRole/getByText。
  • 可选开启：项目 config prototype.e2e: true 时强制。

16.5 spec → Playwright 映射

  • 提取源：#### Scenario:（→HP）/ ##### Exception:（→EX）/ ##### State:（→ST）/ ##### Boundary:（→BND）。
  • 解除"可选→强制"陷阱：维度条件触发（仅含某维度标签才考核）+ 关键字回退（未打标签时从文本提取）。
  • AC 公式：Total = HP×1 + EX×2 + ST×2 + BND×1。
