# 原型生成体系升级提案（P2-6 研究成果）

> **版本**：v0.17.0 研究输出（2026-07-25）
> **来源**：open-design（nexu-io/open-design）源码深度研究
> **前置文档**：`docs/prototype-design-research.md`（v0.3 选型调研）
> **硬约束**：零外部依赖 / 纯 CLI / 自包含 HTML 内核不变。不安装、不调用任何外部设计软件。

---

## 一、研究方法

LT 手动 clone open-design 完整源码到 `docs/external-references/open-design/`，CC 对其五层内容进行系统研究：

| 层 | 目录 | 规模 | 价值判断 |
|---|---|---|---|
| 渲染型模板 | `design-templates/` | ~110 个 | ★★★ 方法论富矿（web-prototype 6 步工作流、layouts.md 骨架库、checklist） |
| 通用工艺规则 | `craft/` | 12 个 | ★★★ 品牌无关恒真规则（anti-ai-slop、排版层级、无障碍基线） |
| 品牌设计系统 | `design-systems/` | ~30 品牌 + `_schema/` | ★★★ token 四层模型权威定义 |
| 流程原子 | `plugins/_official/atoms/` | 16 个 | ★★ direction-picker / critique-theater / diff-review 等 |
| 功能性 skill | `skills/` | 162 个 | ★ ~130 个策展 stub，实质 ~30 个 |

**结论**：app 代码（daemon/Next.js/Electron）对 team-flow 无价值；价值全在纯文本契约层。

---

## 二、核心发现：架构同构

open-design 与 team-flow 共享最深层约束：

> *"Artifacts are generated by agents pasting one brand's :root block into a single `<style>`. There is no global stylesheet... a missing token resolves to nothing and the rule silently breaks."*
> — open-design `design-systems/_schema/` 设计文档

这意味着 open-design 踩过的坑（静默断 token、accent 泛滥、只画有数据态、AI 默认靛蓝）team-flow 必然同样会踩，其防线值得直接继承。**且所有防线都是纯文本契约，与"零依赖 + 子代理 + 文件落盘"架构完全兼容。**

### 需降级适配的两处

| open-design 形态 | team-flow 适配 |
|---|---|
| daemon lint-artifact（机器检查） | reviewer 子代理的 Bash grep 检查 |
| 同会话五席 turns（critique-theater） | 独立 reviewer 子代理的多席 rubric（判据需写得更显式，但独立上下文更抗偏差） |

### team-flow 已有优势（不逊于 open-design）

- 收敛检测（连续两轮无收缩 → 提前转人工）
- 变更履历（design-system.md 迭代记录）
- data-testid E2E 契约（open-design 用 data-od-id，不如 data-testid 通用）
- AskUserQuestion 交互（open-design 用 question-form artifact，不如原生交互）

| 15 | **section 节奏交替规则** | layouts.md 附带（hero→features×3→stats→split→cta） | ★ |

## 六、与现有架构的关系

```
v0.3 调研（prototype-design-research.md）
  └─ 选型结论：本地 HTML 原型内核 + 借鉴 DESIGN.md 概念 ← 不变

v0.15.0 实施（设计增强方案 v0.8 §18.6）
  └─ 内部子代理编排 + 设计系统生命周期 ← 已落地

v0.17.0 研究（本文）
  └─ 19 项缺口 + 三波路线图 ← 方法论深化

Wave 1 (v0.18.0) → Wave 2 (v0.19.0) → Wave 3 (待反馈)
  └─ 从"借鉴概念"升级为"系统性吸收工艺防线"
```

**核心原则**：open-design 的 daemon/SSE/iframe/Electron 层对 team-flow 无价值也不需要；只吸收其纯文本契约层的方法论防线，全部内化为 team-flow 插件内部的 references/ 文件和 agent 提示词。
