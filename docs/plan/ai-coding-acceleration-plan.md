# 内部团队 AI Coding 陪跑设计与规划方案

> 版本：v2.0（修订）｜编制日期：2026-08-04｜状态：待 LT 确认后用于领导汇报
>
> 本文档回答三个问题：
> 1. **为什么现在做** —— team-flow 工作流插件已具备覆盖"模糊需求 → 交付归档"全链路的能力，且有测试门禁体系保障质量，可以作为内部团队 AI Coding 主力工具引入。
> 2. **怎么陪跑** —— 从零搭建基础设施 → 小范围试点 → 陪跑反哺插件 → v1.0.0 规模化基线。
> 3. **做到什么程度** —— team-flow 每个阶段的能力边界、自动化程度、产物与质量门禁，以及产品研发全生命周期各阶段 AI Coding 的具体用法。

---

## 一、背景与目标

### 1.1 背景

内部团队尚未引入 Claude Code（从环境到流程均为空白）。与此同时，本团队已独立打磨出 team-flow 工作流插件（**v0.33.0，24 skills + 15 agents，九套能力合一**），经 33 个版本迭代，已具备从"模糊需求"到"发布归档 + 经验复利"的完整 AI 驱动研发工作流，并通过代码级门禁体系（状态机、hash 校验、测试门禁）保障产物质量。

将 team-flow 引入内部团队，实质是把团队过去半年沉淀的 **AI Coding 方法论 + 工程化门禁** 复制到全公司，而非只引入一个"AI 写代码"的工具。

### 1.2 目标

| 目标 | 描述 | 达成标志 |
|---|---|---|
| **试点验证** | 1-2 个代表性团队用 team-flow 完整跑通研发流程 | 试点团队独立完成 2 个完整迭代（需求→归档） |
| **能力复制** | 团队掌握 AI Coding 工作流，不依赖专人驻场 | 试点团队具备独立操作能力，答疑量下降 |
| **反哺迭代** | 试点反馈结构化回流到插件迭代 | 每迭代沉淀 ≥10 条可追踪改进项 |
| **规模化基线** | v1.0.0 作为对外稳定版本，支撑全量推广 | v1.0.0 发布 + 规模化路线获批 |

### 1.3 总体策略：边迭代、边试点，v1.0.0 做规模化基线

team-flow 当前处于功能完整但仍在快速迭代的"颠簸期"（v0.31→v0.33 一周内 3 个版本，且出现过打包事故、frontmatter 静默降级两类事件）。因此：

- **不等待完全稳定再对外**：功能已覆盖全流程，且核心门禁体系已硬化（测试门禁 v0.32.1、frontmatter 门禁 v0.33.0）。插件只能在真实项目中成熟。
- **试点团队即 beta 用户**：小范围（1-2 团队）先跑，问题通过 workflow-feedback 结构化回流，快速修复，把颠簸控制在可控半径内。
- **v1.0.0 是规模化分水岭**：v1.0.0（成熟版）发布前，只做试点；发布后，才具备向全量团队推广的版本基线。

## 二、team-flow 能力地图：覆盖阶段 × 能力程度 × 产物

### 2.1 总体视图

team-flow 覆盖产品研发的 **需求 → 设计 → 开发 → 测试 → 交付 → 反馈沉淀** 全链路，但**不覆盖生产发布与线上运维**（边界见 2.3）。自动化程度分级：

- **L3 全自动 + 门禁守护**：AI 执行，代码级门禁强制校验产物，人审阅兜底（规划、实现、测试段为主）
- **L2 半自动 + 人工决策点**：AI 产出，人工在关键决策点（DP）确认
- **L1 辅助**：AI 提供建议/生成初稿，人工主导

```
模糊需求
  │
  ▼
[接入层 workflow-bootstrap] ──────────── 既有项目：B1 侦察 → B2 基线 → B3 领域词汇 → B4 目录初始化
  │
  ▼
[产品级编排层 workflow-orchestrator] ──── S1 路径路由 → S2 PRD+原型 → S3 计划 → S4 拆分分发 → S5 全局监控
  │                                        （每阶段转换点：复利检测→捕获→索引→注入）
  ▼
[变更级执行层 workflow-start] ──────────── exploring → specifying → bridging → approved-for-build → executing → closing
  │                                        （debugging 侧路径 / abandoned 终态）
  ▼
[复利回写层] ───────────────────────────── arch-merge → prototype-sync → 经验晋升 → 下一 change/PRD 的 grounding
```

### 2.2 分阶段能力明细

#### 阶段 ① 需求（自动化程度：L2-L3，强覆盖）

| 子能力（skill/agent） | 做什么 | 产物 | 自动化/门禁 |
|---|---|---|---|
| ce-ideate | 创意生成与评估（grounded ideas） | 创意清单 | L2 |
| need-explorer | 交互式澄清意图/scope/约束/成功标准 | change 定义（守 DP-1 门） | L2，人工澄清 |
| ce-brainstorm | 产出结构化 PRD（GTMC D7 业务要件 11 章模板） | `prd/vN/prd.md` | L2 |
| prd-completeness-reviewer | PRD 完整性评审（5 维度：是否够支撑 plan/spec 实施） | `prd/vN/prd-completeness-review.md` | **L3 门禁：冻结前必过** |
| ce-strategy | 产品策略锚点 | `STRATEGY.md` / `CONCEPTS.md`（领域词汇） | L2 |

**能力程度**：需求澄清、PRD 编写、完整性评审全链路覆盖，可做到"模糊一句话 → 可实施 PRD"，这是纯对话式 AI 难以稳定做到的（不评审完整性的 PRD 会在下游失真）。

#### 阶段 ② 设计（自动化程度：L2-L3，强覆盖）

| 子能力 | 做什么 | 产物 | 自动化/门禁 |
|---|---|---|---|
| prototype（env-scout→builder→reviewer 内部编排器） | 本地 HTML 原型：环境探查 → 差异化方向 → 绘制 → 评审循环 | `prototype/`（index/pages/components/assets/flow） | L2，人工评审兜底；**builder 产物落盘硬闸门** |
| design-system | 项目级设计系统独立创建/迭代（base 品牌层 + B/C 端变体） | `design-system.md`（9 段 schema + 5 方向调色板） | L2，用户主导交互 |
| prototype-reviewer | 原型 vs PRD 6 维度一致性评审 | `prototype-auto-review.md` | L3 门禁（循环修正 ≤3 轮） |
| ce-plan | 产品级实施计划：change 拆分 + 依赖 DAG + 高阶技术方向 | `prd/vN/plan.md` | L2 |
| change-split-auditor | plan 拆分质量审计（需求覆盖矩阵、DAG 无环、粒度均衡、字段完整性） | 拆分审计 PASS/FAIL verdict | **L3 必选门禁** |
| architecture-design | 4A+DDD 增量设计：五项检查判定 + 三件套产出 | `changes/<name>/architecture/{architecture,database,api}.md` + SQL | L2，人工确认 |
| architecture-reviewer | 架构设计 6 维度自动审查（A1-A6，≤3 轮循环修正） | 架构审查报告 | L3 门禁 |
| e2e | AC 驱动 Playwright E2E 场景设计 | E2E 场景清单 | L2 |

**能力程度**：从"PRD"到"架构三件套 + 原型 + 计划"的完整设计链路，且每个产出都有自动审查兜底（PRD 完整性、拆分质量、架构 6 维度、原型一致性），防止 AI 产物"看着像那么回事"实则失真。

#### 阶段 ③ 开发（自动化程度：L3 最高，核心区）

| 子能力 | 做什么 | 产物 | 自动化/门禁 |
|---|---|---|---|
| workflow-start | 8 态状态机编排，非法状态转换被代码拦截 | 状态推进记录 | **L3：guard.mjs 硬门禁** |
| spec-writer | 产出四件规划制品 | `changes/<name>/proposal.md` + `specs/*.md` + `design.md` + `tasks.md` | L3：`artifacts_hash` 校验 |
| contract-builder | 规划制品压缩为单一执行握手契约 | `execution-contract.md` + `test-matrix.md` | L3：`contract_hash` + DP-3 批准门 |
| build-executor | 以契约为权威驱动 TDD 批次实施（守 TDD Iron Law） | 代码实现 + 单元/集成测试 | L3：批次门禁 |
| code-reviewer | spec 合规审查（6 步 + 严重级校准 + 测试矩阵合规维度） | 审查报告 | **L3 合并门禁** |
| bug-investigator | 科学方法根因调查（执行期 bug/测试失败） | 根因分析报告（不直接改码） | L2-L3 |
| cross-change-consistency-checker | 多 change 并行时的共享聚合/API 契约/架构锚点漂移检测 | 冲突检测报告 | L3（S5 必选） |

**能力程度**：这是 team-flow 与传统 AI Coding 工具拉开差距的核心区——**实现由"批准的契约"驱动，而非直接对话驱动**。TDD Iron Law（先写测试）、测试矩阵驱动、代码审查门禁，保证 AI 写的代码不是"黑盒产出"。

#### 阶段 ④ 测试（自动化程度：L3，强覆盖，v0.31-v0.33 硬化）

| 子能力 | 做什么 | 产物 | 自动化/门禁 |
|---|---|---|---|
| test-strategy | 测试设计方法论：10+1 种 design_method + 分层策略 + 对抗验证 + 复杂度分级 | `test-matrix.md`（12 列字段） | L3 |
| 测试执行证据 | 对接 maven-surefire / jest / pytest，程序化收集 | `.superpowers/test-evidence/` | **L3：`tf test record`，无手工通道** |
| e2e | Playwright E2E 生成、执行、覆盖率审计 | E2E 测试脚本 + 覆盖报告 | L2 |
| test-merge | 测试复利回写全局测试台账 | `docs/test-ledger/`（INDEX + baselines + patterns） | L3 |

**门禁体系（v0.32.1 事件级硬化后的现状）**：
- `test-matrix-ready`：**approved-for-build → executing 前置门禁**（矩阵存在非空 OR 显式 skip 附理由）
- `tests-passing`：**只认程序化证据**（`tf test record` 落盘），dp_6 自述不再是证据
- 豁免键 = `schema_version`（存量 change 兼容，新 change 不豁免）

> 这是"质量不滑坡"的保障：AI 生成的代码必须有测试矩阵 + 真实测试证据才能关闭 change，杜绝"AI 写了代码但没人验证"。

#### 阶段 ⑤ 交付（自动化程度：L2-L3，覆盖到归档）

| 子能力 | 做什么 | 产物 | 自动化/门禁 |
|---|---|---|---|
| spec-merger | delta spec 合并回主 spec 基 | `specs/<cap>/spec.md`（合并后） | L3 |
| release-archivist | 验证 + closing 总结 + 归档就绪（arch-merge → prototype-sync → 复利晋升） | closing 总结 + `learnings.md` | L2；**L3 门禁：compound-captured**（强制 learnings 或显式 skip） |
| arch-merge / prototype-sync | 全局架构锚点 / UI 契约顺序回写 | `docs/architecture/` + `prototype/` 更新 | L3 顺序约束 |

**能力程度**：交付到"代码合并 + 归档 + 全局文档回写"为止。**生产构建、部署、上线不在此范围**（见边界）。

#### 阶段 ⑥ 反馈与复利（自动化程度：L2，贯穿层）

| 子能力 | 做什么 | 产物 | 自动化/门禁 |
|---|---|---|---|
| ce-compound | 已解决问题沉淀为全局经验（三层索引） | `docs/solutions/`（INDEX + 分阶段 + 经验文件） | L2 |
| workflow-feedback | 工作流问题结构化记录（10 类分类）→ 迭代输入 | `.team-flow/feedback/` | L2 |
| session-handoff | 上下文腐化时压缩为结构化交接文档（10 节） | `.team-flow/handoffs/` | L2 |
| 复利贯穿机制 | 每阶段转换点：检测→捕获→索引→注入（`tf solutions capture/inject/promote`） | 全局经验库 | L2（advisory，不阻断） |

**能力程度**：知识复利是团队资产——每个 change 的经验自动回流，作为下一个需求/下一个 PRD 的 grounding，团队不会"做完就忘"。

### 2.3 能力边界（实事求是）

| 边界 | 说明 | 现状 |
|---|---|---|
| **生产发布/部署** | 构建、发布到生产、灰度 | ❌ 未覆盖（人工/CI 工具），team-flow 到归档为止 |
| **线上监控/告警/运维** | 生产问题监控、告警响应 | ❌ 未覆盖（需既有运维体系），bug-investigator 可辅助线下根因调查 |
| **需求源集成** | JIRA/TAPD 等外部系统自动导入需求 | ⚠️ 半覆盖（TAPD 等通过 MCP 可手动对接，无自动同步） |
| **跨项目组合管理** | 多产品线的组合级规划 | ⚠️ 半覆盖（S5 管多 change，不管多产品线） |
| **非技术/项目管理** | 资源排期、预算、人员管理 | ❌ 未覆盖 |

> 汇报口径建议：**"team-flow 覆盖从需求到归档的完整研发闭环，生产发布与线上运维仍需既有体系"**——不夸大，避免后续被要求能力对不上。

## 三、产品研发全生命周期 × AI Coding 应用蓝图

> 定位说明：**team-flow 是组织级工作流层**（把研发流程标准化、门禁化），**原生 Claude Code 是个人工具层**（日常问答、单点编码、脚本）。两层配合使用。

### 3.1 各阶段 AI Coding 用法一览

| 研发阶段 | 人做什么 | AI 做什么（team-flow） | AI 做什么（原生能力） | 关键产物 | 质量门禁 |
|---|---|---|---|---|---|
| **需求** | 业务背景、价值判断、优先级决策 | `/team-flow:workflow-orchestrator` → ce-brainstorm 产 PRD + prd-completeness-reviewer 评审 | 对话澄清、竞品/资料检索 | `prd/vN/prd.md` | PRD 完整性评审冻结 |
| **原型/设计** | 方向拍板、审美判断、方案选择 | prototype 内部编排器（env-scout→builder→reviewer）+ design-system | 参考图分析、风格建议 | `prototype/`、`design-system.md` | 原型一致性评审 |
| **架构/方案** | 技术选型决策、架构评审 | architecture-design 五项检查→三件套 + architecture-reviewer A1-A6 + ce-plan | 技术预研、方案对比 | `architecture/*.md`、`plan.md` | 拆分审计必选 + 架构审查 |
| **实现** | 业务逻辑理解、疑难问题定位、变更决策 | workflow-start 8 态机：spec-writer→contract-builder→build-executor（TDD 批次）→code-reviewer | 单点编码、重构、脚本、debug | `changes/<name>/` 全套 | 状态机 + hash + TDD + 代码审查 |
| **测试** | 测试策略拍板、异常场景补充 | test-strategy 矩阵 + build-executor TDD + `tf test record` 证据 | 测试数据、调试、覆盖率分析 | `test-matrix.md`、`docs/test-ledger/` | 矩阵门禁 + 程序化证据 |
| **E2E/验收** | 验收标准确认 | `/team-flow:e2e`（AC 驱动 Playwright） | 测试脚本优化 | E2E 脚本 | 覆盖率审计 |
| **交付/归档** | 合并审批、发布决策 | release-archivist（验证+closing+归档）+ spec-merger + arch-merge + prototype-sync | 变更说明、release notes | closing 总结、`learnings.md` | compound-captured |
| **反馈/迭代** | 复盘、优先级 | workflow-feedback + ce-compound + 复利注入 | 汇报材料、知识沉淀 | `.team-flow/feedback/`、`docs/solutions/` | — |

### 3.2 分层使用模型（给团队的手册要点）

```
个人日常（原生 Claude Code）    组织研发（team-flow）          全局资产（复利层）
─────────────────────         ─────────────────────         ─────────────────────
对话式问答 / 单点编码             产品级新需求 → orchestrator       docs/solutions/ 经验库
代码解释 / 重构 / 脚本            change 内操作 → workflow-start   docs/architecture/ 架构锚点
临时工具 / 调试辅助              既有项目 → workflow-bootstrap     prototype/ UI 契约
                              bug → bug-investigator           STRATEGY.md / CONCEPTS.md
```

**三条纪律**：
1. **产品级新需求必须走 orchestrator**（唯一的规范化入口），不用个人对话方式直接写核心代码——否则产物无门禁、无门禁=质量无保障。
2. **门禁不放行 = 不完成**：状态机、hash、测试矩阵、程序化证据是"完成"的定义，不是可绕过的建议。
3. **人工决策点不外包**：DP-1（需求边界）、DP-3（契约批准）、DP-A（方案确认）、架构评审、代码合并审批，永远是人的责任。

## 五、组织与角色

| 角色 | 构成 | 职责 |
|---|---|---|
| **平台小组（CoE）** | 插件维护者 + 陪跑教练（2 人全职） | 插件迭代、基础设施、培训、答疑、试点复盘、规模化路线 |
| **试点团队** | 1 个项目团队，含产品、UI、前端、Java 后端 | 作为 beta 用户真实使用，提供结构化反馈，总结收集 KPI 基线数据 |
| **团队种子/大使** | 试点团队中的积极分子 | 规模化后的内部布道、FAQ 维护、经验分享 |

**试点团队选择标准**：有真实业务价值（不是 demo）、需求迭代真实活跃、技术栈有代表性、Leader 明确支持、成员有基本 AI 工具使用意愿。

**投入估算（试点期约 7 周）**：
- 平台小组：**2 人全职**投入陪跑（插件迭代 + 陪跑 + 答疑）
- 试点团队：成员约 30-50% 时间参与培训与首批落地，之后回归业务节奏
- 关键：**陪跑是"陪同跑通 + 教会方法"，不是"代为开发"**，避免团队依赖。

## 六、风险与依赖

| 风险 | 等级 | 说明 | 对策 |
|---|---|---|---|
| 插件颠簸期稳定性 | 高 | 一周 3 版本、有事件级事故（打包/静默降级） | 试点即 beta；升级窗口协商；v1.0.0 前不承诺规模化；关键修复优先 |
| 首批体验影响信任 | 高 | 首批用户遇到坑会伤口碑，一旦流失难召回 | 陪跑兜底（有人兜着）；问题快速修复；透明度（已知问题清单）；正向激励（首批 = 共建者） |
| 安全合规 | 高 | 密钥泄露、代码外传外部 API、敏感数据进上下文 | **采用国内模型 API（如 DeepSeek）降低跨境数据风险**；密钥治理规范 + CI 扫描；代码外传白名单；MCP 权限最小化 |
| 成本 | 中 | token 用量随规模上升 | 用量监控；上下文优化（team-flow 已做渐进式披露控制上下文）；评估国内模型 API 计费组合 |
| 团队接受度 | 中 | 抵触或过度依赖 | 分层次培训；门禁是保护不是束缚；示范"AI 提高研发质量"而非"AI 替代人" |
| 试点范围偏差 | 中 | 试点项目选择不当 → 结论失真 | 选择标准前置（真实价值 + 代表性）；复盘指标预先定义 |

## 七、汇报要点（TL;DR）

1. **交付物成熟**：team-flow v0.33.0（24 skills + 15 agents）已覆盖"模糊需求 → 交付归档"完整研发闭环，含代码级质量门禁（状态机 / hash / 测试矩阵 / 程序化测试证据），是内部 AI Coding 主力的可行底座。
2. **策略**：边迭代、边试点；1 个试点团队先行，v1.0.0（10 月初）作为规模化基线。
3. **日程**：8/4-8/8 插件完善 → 8/17 准备启动 → 8/24-9/19 陪跑期（4 周）→ 9/22-10/11 复盘 + v1.0.0 发布（约 7 周）。
4. **投入**：2 人全职陪跑 + 试点团队部分时间。
5. **底层模型**：国内模型 API（如 DeepSeek），降低合规与网络风险。
6. **价值主张**：不是引入"AI 写代码工具"，而是把团队沉淀的 **AI 研发方法论 + 质量门禁** 复制到全公司；需求到归档的每个环节有门禁、有产物、有知识复利，质量不滑坡。
