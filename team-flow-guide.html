Team-Flow 工作流指南与制品链详解

版本 0.22.5 | 完整的 AI 驱动开发工作流系统

Team-Flow 是一个 23 skills + 8 agents 的统一插件系统，通过明确的制品链和状态机， 将模糊需求转化为可执行的代码实现。本文档帮助你快速理解如何使用 Team-Flow， 以及每个阶段会产出什么制品、依赖什么制品。

🚀 快速入门

安装

1. 安装 Team-Flow

Team-Flow 作为 Claude Code 插件安装：

# 在 Claude Code 中安装
/plugin install team-flow

安装后，你会获得 23 个 skills 和 8 个 agents，覆盖从需求澄清到代码实施的完整流程。

初始化

2. 首次使用：Bootstrap 阶段

首次使用 Team-Flow 时，需要执行 Bootstrap 阶段建立基线：

# 在 Claude Code 中
/tf workflow-bootstrap

Bootstrap 会执行：

  • B1: 代码库侦察（扫描项目结构、技术栈）
  • B2: 架构基线文档化（生成 docs/architecture/baseline.md）
  • B3: 领域词汇提取（生成 CONCEPTS.md）
  • B4: 目录初始化（创建 .team-flow/ 目录）
启动

3. 开始新需求：产品级编排

当你有新需求时，使用产品级编排器：

# 在 Claude Code 中
/tf workflow-orchestrator

然后描述你的需求，编排器会自动引导你完成 S1-S5 阶段。

执行

4. 实施变更：变更级工作流

当产品级编排完成后，进入具体的变更实施：

# 在 Claude Code 中
/tf workflow-start

变更级工作流会引导你通过 8 个状态完成实施。

🔍 各阶段详解

Bootstrap 初始化阶段 - 建立项目基线

目标

分析现有项目，建立架构基线和领域词汇，为后续工作流提供基础。

步骤详解

步骤 动作 产出 说明
B1 代码库侦察 - 运行 recon-probe.sh 扫描项目结构、技术栈、依赖
B2 架构基线文档化 docs/architecture/baseline.md 记录当前架构状态，作为增量设计的 As-Is 基线
B3 领域词汇提取 CONCEPTS.md 提取项目领域词汇，建立统一语言
B4 目录初始化 .team-flow/ 创建工作流状态目录

判断标准

如果 docs/architecture/baseline.md 已存在，Bootstrap 会自动跳过。

Orchestrator 产品级编排 - S1-S5 阶段

目标

将模糊需求转化为明确的变更列表，每个 change 都有清晰的 scope、AC 和依赖关系。

S1: 路径路由器

输入 动作 输出
用户需求描述 判断入口路径（7种路径） 确定执行策略

7种入口路径：

  1. 新需求（完整 S1-S5）
  2. 续版（跳过 S1-S2）
  3. 快速迭代（跳过 S1-S3）
  4. 单个 change（跳过 S4）
  5. hotfix（简化流程）
  6. tweak（微调）
  7. 原型补跑/重跑

S2: PRD 产出

输入 动作 输出
需求描述 ce-brainstorm + prd-completeness-reviewer prd/vN/prd.md

关键约束：PRD 冻结前必须通过 5 维度完整性评审。

S3: 计划阶段

输入 动作 输出
PRD ce-plan（入口问定 plan_mode） prd/vN/plan.md

plan.md 内容：change 拆分方案 + 依赖关系 + 高阶技术方向（不含接口清单）。

S4: 拆分验证与分发

输入 动作 输出
plan.md change-split-auditor 审计 changes/<name>/ 目录 + change-brief.md

关键约束：必须通过拆分审计（PASS 才能创建 changes/ 目录）。

change-brief.md 结构：

  • Frontmatter: upstream_source, upstream_req_id, upstream_plan_ref, upstream_change_id, plan_hash
  • Body: Scope, 约束, AC 列表, 全局技术方向, PRD & plan 引用

S5: 全局监控（可选）

触发条件 动作 输出
change 数量 ≥ 2 跨 change 一致性检查 + 复利晋升 监控报告
Workflow-Start 变更级工作流 - 8 态状态机

目标

引导每个 change 通过 8 个状态，从探索到实施完成。

8 态状态机

exploring
需求澄清
specifying
规格定义
bridging
契约构建
approved-for-build
等待批准
executing
实施中
debugging
调试
closing
收尾
abandoned
放弃

状态转换详解

exploring → specifying

触发条件：需求已清晰，需要定义规格

Guard 检查：artifacts-exist（proposal.md, specs/, design.md, tasks.md）

关键动作：调用 architecture-design 子代理，判断是否涉及架构变更

状态写入：

dp_0_decisions, dp_0_result, dp_0_confirmed, dp_0_timestamp
arch_design_decision, arch_design_reason, arch_design_timestamp, arch_design_artifacts
specifying → bridging

触发条件：规格已定义，需要构建执行契约

Guard 检查：artifacts-exist, schema-valid

bridging → approved-for-build

触发条件：执行契约已构建，等待批准

Guard 检查：artifacts-exist, schema-valid, contract-fresh, dp-gate-passed

approved-for-build → executing

触发条件：用户批准执行契约

Guard 检查：artifacts-exist, contract-fresh, dp-gate-passed, execution-plan-ready

状态写入：dp_4_result, dp_4_timestamp（通过 tf execution plan 命令）

executing → closing

触发条件：实施完成，准备收尾

Guard 检查：tasks-complete, tests-passing, specs-merged, execution-plan-ready, execution-reviews-passed

executing ↔ debugging

触发条件：实施过程中遇到 bug 或测试失败

executing → debugging：无 guard 检查（紧急通道）

debugging → executing：contract-fresh, execution-plan-ready

Fast-Path 路由

对于简单的变更，可以走快速路径：

  • hotfix：跳过 need-explorer 和 spec-writer，直接到 contract-builder
  • tweak：跳过 need-explorer、spec-writer、contract-builder，直接到 build-executor
  • DP-0 处理：hotfix/tweak 隐式跳过 DP-0（dp_0_confirmed 保持 null），因为意图已明确
Architecture-Design 架构设计门控 - 4A+DDD

目标

判断变更是否涉及架构变更，如果涉及则执行 4A+DDD 增量设计。

五项检查

architecture-design 子代理会执行五项检查，判断是否涉及架构变更：

  1. 聚合变更：是否新增/修改聚合或聚合根？
  2. 限界上下文变更：是否涉及限界上下文边界变化？
  3. 读写模型变更：是否涉及 CQRS 写模型或读模型变化？
  4. API 变更：是否涉及 API 新增/变更？
  5. DB schema 变更：是否涉及数据库表结构、字段、索引变更？

输出结构

changes/<name>/architecture/
├── architecture.md   # DDD 增量设计（聚合、限界上下文、Context Map）
├── database.md       # 数据库增量设计（写模型、读模型、Schema 变更）
└── api.md            # API 增量设计（Command、Read、Query）

职责边界（v0.22.5 修复）

角色 职责 状态写入
architecture-design 判断 + 产出（五项检查 + 架构设计文档） ❌ 不负责状态写入
workflow-start reasonableness check + 状态写入 ✅ 写入 arch_design_* 字段

下游消费

architecture/*.md 会被 spec-writer 消费，用于约束 design.md 和 tasks.md 的设计。

Compound 复利贯穿 - 全局知识沉淀

目标

将每个 change 的经验沉淀为全局知识，形成复利效应。

关键 Skills

Skill 职责 产出
ce-compound 经验沉淀 docs/solutions/*.md, CONCEPTS.md
ce-strategy 策略锚定 STRATEGY.md

触发时机

  • 每个阶段转换点：检测→捕获→索引→注入
  • change 完成：arch-merge + prototype-sync + 复利晋升

💡 最佳实践

1. 遵循制品链依赖关系

每个制品都有明确的生产者和消费者，不要跳过必要的制品产出。

# ✅ 正确流程
PRD → Plan → Change-Brief → Proposal → Specs → Design → Tasks → Execution-Contract → 实施

# ❌ 错误流程
直接开始实施，跳过设计和规格定义

2. 重视 Guard 检查

Guard 检查是工作流的质量门禁，确保每个状态转换都满足前置条件。

# 在状态转换前，先运行 guard 检查
tf runtime guard check changes/my-feature exploring specifying --json

# 如果检查失败，根据错误信息补充缺失的制品或条件

3. 充分利用架构设计门控

architecture-design 子代理会自动判断是否涉及架构变更，如果涉及则产出架构设计文档。

# architecture-design 会执行五项检查：
# 1. 聚合变更
# 2. 限界上下文变更
# 3. 读写模型变更
# 4. API 变更
# 5. DB schema 变更

# 如果任一检查为"是"，则产出 architecture/*.md
# 如果全部为"否"，则返回 skipped

4. 合理使用 Fast-Path

对于简单的变更（hotfix 或 tweak），可以走快速路径，但仍然需要遵循基本的 guard 检查。

# hotfix: 跳过 need-explorer 和 spec-writer
# 但仍然需要：contract-builder (minimal) + DP-3 批准 + execution-plan

# tweak: 跳过 need-explorer, spec-writer, contract-builder
# 但仍然需要：architecture-design 门控检查

5. 重视复利沉淀

每个 change 完成后，使用 ce-compound 和 ce-strategy 将经验沉淀为全局知识。

# 在 change 完成后，执行复利晋升
/tf ce-compound

# 这会产出：
# - docs/solutions/*.md（解决方案）
# - CONCEPTS.md（更新领域词汇）
# - STRATEGY.md（更新产品策略）

6. 使用模板保证一致性

v0.22.5 新增了 4 个标准模板，使用它们可以保证制品结构一致。

# 使用 change-brief 模板
tf runtime asset write changes/my-feature/change-brief.md --template change-brief

# 使用 architecture 模板
tf runtime asset write changes/my-feature/architecture/architecture.md --template architecture
tf runtime asset write changes/my-feature/architecture/database.md --template database
tf runtime asset write changes/my-feature/architecture/api.md --template api

❓ 常见问题

Q1: 为什么我的状态转换被阻断了？

原因：状态转换需要通过 guard 检查，检查失败会被阻断。

解决方法：

  1. 运行 guard 检查，查看具体的失败原因：
    tf runtime guard check <change-dir> <from-state> <to-state> --json
  2. 根据错误信息补充缺失的制品或条件
  3. 重新尝试状态转换
Q2: arch_design_* 字段无法写入？

原因：v0.22.5 之前的版本，arch_design_* 字段不在 SETTABLE_FIELDS 中，无法通过 tf state set 写入。

解决方法：升级到 v0.22.5 或更高版本。

临时方案（v0.22.4）：直接编辑 .team-flow.yaml 文件，手动添加字段。

Q3: dp_4_result 无法写入？

说明：这是设计意图，不是 bug。

正确做法：使用 tf execution plan 命令，它会自动写入 dp_4_result 和 dp_4_timestamp。

# ✅ 正确做法
tf execution plan changes/my-feature --mode full --confirm --reason "实施完整功能" --wave "w1:parallel:task1,task2"

# ❌ 错误做法
tf state set changes/my-feature dp_4_result "..."  # 这会失败
Q4: change-brief.md 应该由谁产出？

生产者：orchestrator S4 阶段

消费者：need-explorer, spec-writer, architecture-design

产出时机：S4 拆分验证通过后，为每个 change 创建 change-brief.md

关键内容：

  • Frontmatter: upstream_source, upstream_req_id, upstream_plan_ref, upstream_change_id, plan_hash
  • Body: Scope, 约束, AC 列表, 全局技术方向, PRD & plan 引用
Q5: 什么时候需要产出 architecture/*.md？

判断标准：architecture-design 子代理会执行五项检查

  • 聚合变更
  • 限界上下文变更
  • 读写模型变更
  • API 变更
  • DB schema 变更

如果任一检查为"是"，则需要产出 architecture/*.md。

如果全部为"否"，则返回 skipped，不需要产出。

Q6: hotfix 和 tweak 有什么区别？
维度 hotfix tweak
适用场景 紧急修复 微调
跳过阶段 need-explorer, spec-writer need-explorer, spec-writer, contract-builder
仍需执行 contract-builder (minimal), DP-3, execution-plan architecture-design 门控
DP-0 处理 隐式跳过（dp_0_confirmed 保持 null） 隐式跳过（dp_0_confirmed 保持 null）
