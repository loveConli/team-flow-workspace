# LT 技能锻造炉（Skill Forge）

从一段 SOP 里锻造出高质量、可复用的 Skill。本技能融合 Anthropic 官方 Skill 方法论与《Skill 高质量编写与使用指南》的质量标准，并在"动笔前"增加一道识别关（Phase 0），避免把一次性任务或低价值内容做成 skill。

**核心理念：Skill 不是写出来的，是从真实工作流里"萃"出来的。** 它沉淀的是"高语境"经验——个人/团队特有的坑、边界、默认规则——而非 LLM 本就会的常识。低语境（API 文档、编码常识）模型自己知道，写出来零增益还增加上下文负担；高语境（只有你清楚的坑与边界）才是 Skill 的真正价值。

---

## 与用户的沟通

用户技术背景差异很大。聚焦"这个技能能帮你解决哪一类问题"，而非技术实现。需要提技术概念时附简短解释。触发短语、description 写法由你负责，不要让用户操心。

---

## 全流程速览

- **Phase 0｜创建前识别**（本技能增强核心）：判断该不该做 + 萃取 SOP
- **Phase 1｜需求理解**：补全用户意图，一轮对齐
- **Phase 2｜编写技能**：init 骨架 + 写 SKILL.md（含质量增强）
- **Phase 3｜注册交付**：`ima_skill_create -d` 注册

> 关键差异：Phase 0 是普通创建技能最容易缺的一步。没有它，容易把"一次性任务"或"LLM 本就会的事"做成 skill，浪费上下文且零增益。

---

## Phase 0：创建前识别（SOP 萃取）

动笔前先过两道关。任何一道不过，先补识别，别急着写。

### 0.1 「该不该做」过滤

用两个滤镜判断是否为 skill 候选：

- **频次 / 复用滤镜（定义）**：会重复发生吗？解决的是「一类问题」还是「一次性任务」？只有能抽象成"一类"才值得沉淀；单次任务直接做掉即可。检验：能否用一句话说清它处理的"哪一类"问题？说不清 → 还是具体任务，不是候选。
- **价值 / 痛点滤镜（因果）**：高频、易错、耗时长、或依赖"只有老手知道的隐性经验"？对照 Anthropic 标准——是**补知识差**（团队特有坑/边界）还是**补执行差**（自动化重复操作）？两者都是好候选；若两者都不是（只是重复 LLM 本就会的），不值得做。

**不过关的常见信号**：用户要的是"帮我做这件事"（一次性）→ 直接做，不建 skill；做出来的内容 LLM 本来就会、没有高语境增量 → 识别失败。

### 0.2 SOP 萃取（从工作流里把流程"萃"出来）

- **回溯法（最可靠）**：从刚完成的任务提取——用过的工具、执行步骤、用户做的修正、输入/输出格式。比让用户凭空描述准十倍。
- **异常萃取 → 这就是 Gotchas 来源**：正常路径用户能说，精华在异常分支。主动问："这一步卡住过吗？什么情况会偏？""有没有文档没写但必须额外做的？"这些回答即高语境坑点。
- **抽象到「一类」（去特例、留结构）**：把"这篇 PDF"→"任意英文文档"，把"这次字段"→"结构化输出模板"。保留决策结构，去掉一次性参数。
- **六要素透镜检验**（定义/分类/因果/流程，详见 `references/need-identification.md`）：
  - 定义：处理哪一类问题？边界清楚吗？
  - 分类：9 类里的哪类？知识差 or 执行差？
  - 因果：每步"为什么必须这样"——哪些是可变决策点（留给 AI）、哪些是不可变约束（写死）？
  - 流程：只读步骤标题能串成通顺操作链吗？长流程有没有确认门？

### 0.3 三问自检（识别对不对）

1. **触发边界**：能一句话说清"何时触发、何时不触发"？说不清 → 需求/SOP 未界定好。
2. **可执行性**：能列 2+ 个真实"输入→输出"示例？列不出 → SOP 还停在概念层。
3. **反向排除**：写出来 LLM 本就会、无高语境增量 → 该做的是任务不是 skill。

三问全过 → 进入 Phase 1。

## Phase 1：需求理解

用户开口时常已带大量信息。先吃透已说的，只追问真正缺失的。

**信息获取优先级：**
1. **对话历史优先**：若用户刚完成任务（"把刚才的做成技能"），从对话历史提取工作流，通常无需额外追问，直接输出理解让用户确认。
2. **用户描述中提取**：用户说"帮我创建公众号长文的 skill，我是 AI 行业的"已含目标/领域/输出形式，不必逐条追问。
3. **合理推断**：从技能类型推断大部分细节，整理好一次性让用户确认/调整。

**只问用户需求**：聚焦"这个技能要帮你做什么"。触发短语、description 写法由你负责。
**一轮对齐**：最多追问一轮，附少量需用户决定的选项一次性发出。确认后进入 Phase 2。

## Phase 2：编写技能

先用 init_skill.py 初始化骨架（模板已内置 `## 不适用场景` 与 `## Gotchas` 章节），再编辑 SKILL.md：

```bash
python3 /sandbox/workspace/skills/lt-skill-forge/scripts/init_skill.py {name}
```

脚本生成 SKILL.md 模板 + scripts/references/assets 三目录（含示例），按需替换或删除空目录。

### SKILL.md 组件

- **name**：kebab-case，≤64 字符。从核心词转换——"合同审查"→`contract-review`，"周报生成"→`weekly-report`。
- **description**：触发机制核心。第一句说做什么 → 中间列触发条件（具体短语/意图关键词）→ 最后说不适用边界。例："合同审查与风险分析。当用户提到审合同、检查合同、合同风险评估，或上传合同/协议文件希望分析时触发。不适用于合同起草、翻译或咨询。"
  - 中文技能用「当用户…时触发」等效英文 "Use when"；description 控制在 ~200 字符内，过长细节移入正文。
- **正文必含章节（质量增强）**：
  - `## 概述`：1–2 句说明做什么。
  - `## 工作方式 / Phase`：流程步骤（祈使、有序、说做什么；解释 WHY 让 Agent 边界自主判断）。
  - `## 示例`：**≥2 个**覆盖典型场景的输入→输出对（1 个像特例，2 个为最低）。
  - `## 不适用场景（When NOT to use）`：**独立反触发章节，单一最大质量信号**。列 3–5 个不该触发的场景；若想不出说明范围过宽需拆分。
  - `## Gotchas / 常见坑`：**信息密度最高的部分**。沉淀真实执行反复踩的坑、隐性边界、与默认解法的偏离点。这是 Skill 区别于"说明书"的关键。
  - `## 资源目录`：scripts/（确定性操作）、references/（按需加载）、assets/（输出用模板等）。

### 技能结构（渐进式披露）

```
skill-name/
├── SKILL.md（必填，<400 行）
└── 附属资源（可选）
    ├── scripts/    - 可执行脚本（确定性/重复性任务）
    ├── references/ - 按需加载的参考文档
    └── assets/     - 输出中使用的文件（模板、图标等）
```

三级加载：① 元数据（name+description）常驻 → ② SKILL.md 触发时加载 → ③ 附属资源按需加载。SKILL.md 接近上限时，将参考拆入 `references/` 并说明何时读取。

### 编写风格

向模型解释事情为什么重要，而非堆砌生硬"必须"。让技能具有通用性而非局限于特定示例。

### 安全原则

技能不得包含恶意软件、攻击代码，或旨在未授权访问、数据窃取的内容。

### 避免的做法

1. 重复 LLM 已有能力——提供结构化流程或领域知识，而非"请用优美语言写作"
2. 引用不存在的工具——编写前检查自身工具列表
3. 只说 MUST 不说 WHY——解释原因让 Agent 边界自主判断
4. 超长不拆分——超过 400 行拆入 `references/`
5. 没有工作流示例——至少 2 个覆盖典型场景的示例
6. 缺少确认门——长流程倾向有用户确认点
7. 没有 Gotchas——只写"说明书"不写踩过的坑（高语境缺失）
8. 无独立不适用场景章节——范围未界定

### 质量自查

生成后逐项自查（发现问题直接修复，不展示给用户）。完整清单见 `references/quality-checklist.md`，关键项：

| 检查项 | 标准 |
|--------|------|
| frontmatter | name kebab-case ≤64；description 含触发条件 + 不适用边界 |
| 章节齐全 | 有 `## 示例`（≥2）、`## 不适用场景`、`## Gotchas` |
| TODO 残留 | 无 `[TODO` 占位符残留 |
| 流程清晰度 | 只读步骤标题能串成操作链 |
| 输出格式 | 明确定义产出物格式与存放位置 |
| 行数控制 | SKILL.md ≤400 行，细节拆 references/ |

## Phase 3：注册交付

```bash
ima_skill_create -d /sandbox/workspace/skills/{name}/
```

注册后告知用户：技能已提交，审核通过后在新对话中生效；以后修改可说"修改我的 XX 技能"。
