# 需求与 SOP 识别方法论（Phase 0 详版）

本文件是 lt-skill-forge 的 Phase 0 详解。核心前提：**skill 创建的实质，是对一段 SOP 的沉淀**。创建前必须先识别"用户真实需求"和"要沉淀的 SOP 是什么"，否则容易造出低价值或一次性技能。

---

## 一、识别真实需求——判断「该不该做成 skill」

用户嘴上说的，往往不是真正该沉淀的 SOP。用三个滤镜剥开：

### 1. 频次 / 复用滤镜（定义要素）
- 问：这件事会重复发生吗？它解决的是「一类问题」还是「一次性任务」？
- 只有能抽象成「一类」才值得沉淀。单次任务直接做掉即可，不必 skill。
- 检验：能不能用一句话说清它处理的"哪一类"问题？说不清 → 还是个具体任务，不是 skill 候选。

### 2. 价值 / 痛点滤镜（因果要素）
- 痛点在哪？高频、易错、耗时长、依赖"只有老手知道"的隐性经验？
- 对照 Anthropic 判断标准：**补知识差**（团队特有坑/边界）还是**补执行差**（自动化重复操作）？两者都是好候选；如果两者都不是（只是重复 LLM 本就会的），不值得做。

### 3. 用户说的 ≠ 用户要的（以终为始）
- 用户常说"我想要个 XX 功能"，实际要的是"解决某类问题的稳定能力"。
- 用终态思维反推：这个 skill 交付后，用户的"终态"是什么？是他少操心一件事、还是 AI 能自主跑完一段流程？终点清楚了，需求边界才清楚。

---

## 二、识别 SOP 本体——从工作流里萃取流程

### 1. 回溯法（从已完成任务提取）
最可靠的来源。从刚做过的任务里提取——用过的工具、执行步骤、用户做的修正、输入/输出格式。比让用户凭空描述准十倍。

### 2. 异常萃取 → 这就是 Gotchas 的来源
正常路径用户自己能说，但 SOP 的精华在异常分支。主动问：
- "这一步卡住过吗？什么情况下会偏？"
- "有没有文档没写、但必须额外做的？"
这些边界回答，就是高语境坑点区（信息密度最高的部分）。

### 3. 抽象到「一类」（去特例、留结构）
把这次具体做法泛化：把"这篇 PDF"变成"任意英文文档"，把"这次的字段"变成"结构化输出模板"。保留决策结构，去掉一次性参数。

### 4. 六要素透镜检验
- **定义**：这个 SOP 处理哪一类问题？边界清楚吗？
- **分类**：属于 9 类里的哪类？知识差 or 执行差？
- **因果**：每一步"为什么必须这样"——区分哪些是可变决策点（留给 AI）、哪些是不可变约束（写死）？
- **流程**：只读各步骤标题，能串成通顺操作链吗？长流程有没有确认门？

---

## 三、三问自检（识别对不对）

1. **触发边界**：能一句话说清"何时触发、何时不触发"？说不清 = 需求或 SOP 还没界定好。
2. **可执行性**：能列出 2+ 个真实"输入→输出"示例吗？列不出 = SOP 还停留在概念层。
3. **反向排除**：如果写出来的内容 LLM 本来就会、没有高语境增量 → 识别失败，该做的是任务不是 skill。

三问全过 → 进入 Phase 1 需求理解。

---

## 四、与现有工具的衔接

ima-skill-creator 的 Phase 1 已是一套需求识别机制（对话历史优先 / 描述提取 / 合理推断 / 一轮对齐），但它偏"对话内补全"——擅长把已浮现的需求填完整，**缺两样**：
- ❌ "该不该做"的过滤（频次 / 知识差-执行差判断）——容易把一次性任务也做成 skill；
- ❌ "抽象到一类"的显式步骤——容易沉淀成"这次怎么做"而非"这类怎么做"。

本 Phase 0 正是补上这两处，让每个 skill 在动笔前先过识别关。
