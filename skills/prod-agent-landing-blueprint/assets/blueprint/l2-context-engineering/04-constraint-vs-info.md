# 约束型 vs 信息型上下文区分（L2 上下文工程）

> 报告引用: §4 上下文工程（五种策展策略）
> 定位: 区分「必须遵守的规则」和「可变的事实信息」，防止规则随会话压缩丢失或信息被错误当作规则固化。
> 标签: 【来源已核验✅】

## 定义

| 类型 | 定义 | 加载位置 | 生命周期 | 可变性 | 示例 |
|------|------|----------|----------|--------|------|
| **约束型上下文** | 必须遵守的规则、禁止模式、完成标准 | 系统提示层（CLAUDE.md / AGENTS.md） | 永久（持久提示层） | 低频变更（需走变更流程） | "禁止直接 push 到 main"、"所有代码须 TDD"、"覆盖率 ≥ 80%" |
| **信息型上下文** | 可变的事实信息、当前状态、临时数据 | 会话层（动态检索、NOTES.md、status-tracker） | 会话/需求级 | 高频变更 | "当前 phase=IMPLEMENTING"、"T-003 已完成"、"CR 评论 #42 未 resolve" |

## 区分标准

> 判断一条上下文是「约束型」还是「信息型」的简单标准：
> **如果删除它，Agent 会做出错误决策 → 约束型；如果删除它，Agent 只是缺少信息但不犯错 → 信息型。**

| 检查项 | 约束型 | 信息型 |
|--------|--------|--------|
| 是否影响 Agent 的「做什么」决策？ | 是 | 否（仅影响「怎么做」） |
| 是否涉及禁止/必须模式？ | 是 | 否 |
| 变更是否需要走变更流程？ | 是 | 否（可直接更新） |
| 丢失后是否导致系统级错误？ | 是 | 否（仅影响效率） |
| 是否应写入持久提示层？ | 是 | 否 |

## 加载策略

### 约束型上下文加载
- **文件**: `CLAUDE.md` / `AGENTS.md`
- **加载时机**: 每次会话启动时自动加载（Claude Code / Codex 自动读取）
- **更新方式**: 走变更流程（spec → plan → CR → 合并），**不可**在会话中直接修改
- **持久性**: 跨会话、跨需求永久生效

### 信息型上下文加载
- **文件**: `status-tracker.md` / `NOTES.md` / `audit-log.jsonl` / 动态检索结果
- **加载时机**: 会话启动时读取最近状态；会话中按需检索
- **更新方式**: 会话中实时更新（如完成一个 task 即更新 status-tracker）
- **持久性**: 需求级；结项后蒸馏为稳定知识（部分转为约束型）或归档

## 转换规则（约束 ↔ 信息 互转）

```
信息型上下文（多次验证稳定）
  │ 结项审视（superai-finish）
  │ "反复出现的问题" → 约束型
  ▼
约束型上下文（写入 CLAUDE.md / AGENTS.md）
  │ 新场景发现例外
  │ 需人工审查确认
  ▼
信息型上下文（降级为临时规则）
```

1. **信息 → 约束**: 某条信息在多个需求中反复验证为稳定规则 → 结项审视时写入 CLAUDE.md/AGENTS.md
2. **约束 → 信息**: 某条约束发现不适用于新场景 → 走变更流程从 CLAUDE.md/AGENTS.md 移除，降级为 NOTES.md 中的临时备注

## 常见错误与避免

| 错误 | 后果 | 避免方式 |
|------|------|----------|
| 将约束型上下文写入 NOTES.md | 会话压缩后丢失，Agent 违规 | 约束型必须写入 CLAUDE.md/AGENTS.md |
| 将信息型上下文写入 CLAUDE.md | 频繁更新导致持久提示层膨胀、混乱 | 信息型写入 status-tracker/NOTES.md |
| 不区分两种类型 | 上下文污染，规则与事实混杂 | 每次写入前用「删除测试」判断 |

## 标准词表（建议）

> 约束型文本中建议使用的标准关键词，帮助 Agent 自动识别。

- **必须/禁止/不可/严禁** → 约束型（规则）
- **当前/最近/本次/临时** → 信息型（状态）
- **建议/推荐/优先** → 信息型（指导，非强制）
- **违反…将导致…** → 约束型（后果声明）
