# spec.md — 需求规格说明书模板（SDD 阶段0）

> 报告引用: §3 提示词工程 / §6.2 阶段1 需求澄清 / §8 Pipeline
> 定位: SDD 三文档第一阶：spec → plan → tasks。从用户视角描述需求意图。
> 标签: 【来源已核验✅】

## 一、用户故事（User Story）
> 从用户视角描述需求意图，使用 "作为...我想要...以便..." 格式。

作为 **[角色]**，我想要 **[功能]**，以便 **[价值/目的]**。

## 二、功能需求（Functional Requirements）
> 具体要实现什么。按优先级排序，使用可验证的表述。

1. **[FR-001]** 需求描述...
2. **[FR-002]** 需求描述...
3. **[FR-003]** 需求描述...

## 三、非目标边界（Non-Goals）
> 明确什么**不在**本次需求范围内，防止范围蔓延。

- ❌ 非目标1：...
- ❌ 非目标2：...

## 四、验收标准（Acceptance Criteria）
> 明确的完成判据，可验证、可度量。

- [ ] AC-1: ...（可验证的条件）
- [ ] AC-2: ...（可验证的条件）
- [ ] AC-3: ...（可验证的条件）

## 五、风险（Risks）
> 可能的技术风险和业务风险。

| 风险ID | 描述 | 概率 | 影响 | 缓解措施 |
|--------|------|------|------|----------|
| R-001 | ... | 高/中/低 | 高/中/低 | ... |
| R-002 | ... | 高/中/低 | 高/中/低 | ... |

## 六、待确认问题（Open Questions）
> 需要人工决策的开放问题。这些问题须在 `CLARIFYING` 阶段确认。

- [ ] Q-1: ...（问题描述）→ 待确认人: ... → 期望确认日期: ...
- [ ] Q-2: ...（问题描述）→ 待确认人: ... → 期望确认日期: ...

## 七、状态机记录
> 供 status-tracker 机读块引用
- 当前 Phase: `DRAFT` → `CLARIFYING`（本 spec 产出后进入 `CLARIFYING`）
- 下一活动: 需求澄清（superai-clarify skill）
- 质量门: 人工确认（确认后方可进入 `DESIGNING`）

---
> 填写说明：每个需求一份 spec.md。产出后进入 `CLARIFYING`，由 superai-clarify 生成 requirements 并人工确认。
